# ADR 0010: Ticket workflow across server and local desktop modes

- Status: Accepted
- Date: 2026-10-22

## Context

Independent professionals need a compact way to track work requests from analysis through production, with client association and effort estimates. The workflow must support the browser, connected Tauri, and fully local desktop with the same domain rules and durable behavior.

## Decision

- A ticket belongs to one workspace and may reference one active client in that workspace. A missing client ID means the ticket is internal. Server handlers derive the acting user from the authenticated session and authorize each workspace operation through active membership; ownership and audit actors are not accepted from clients.
- The `ticket` table is managed through Drizzle migrations. It stores a positive OT number unique within its workspace, title, description, priority (`urgent`, `high`, `medium`, `low`), status (`requested`, `analysis`, `development`, `review`, `correction`, `delivered`, `production`), estimated/worked hours, coding-finished and production timestamps, stable ID, version, soft-delete metadata, and create/update audit fields. OT numbers remain reserved after soft deletion.
- New tickets suggest `max(ot_number) + 1`, including soft-deleted records, and users may edit the suggestion. PostgreSQL and SQLite enforce uniqueness. Web replicas index cached OT numbers and reject local duplicates; if independent offline devices suggest the same number, the first server commit wins and the other create is retained as a failed, editable mutation so the user can assign a different number and retry.
- The coding-finished timestamp is assigned when a ticket enters `delivered`. The production timestamp is assigned when it enters `production`. Timestamps are generated by the authoritative store, cannot be supplied by clients, and remain as milestone history if the ticket later changes status. Re-entering either status records the new transition time.
- The collection screen uses 25-item keyset pages ordered by immutable `created_at` and ID. Server cursors preserve PostgreSQL timestamp precision so closely created records cannot be skipped when mapped to browser dates. Filters and search run before the limit. The OT number has its own table column and a visible label on Kanban cards. The default view is a compact table; users can switch to a Kanban view. The view preference is durable on the current device.
- Web and connected Tauri use the same API and share a durable IndexedDB ticket replica and mutation queue. Each local write commits the ticket state and idempotent mutation together before showing it as locally saved. Synchronization retries pending writes and merges bounded pages, including tombstones. Server membership remains authoritative when online.
- The IndexedDB replica records whether bounded hydration has completed for each user/workspace. Until then the UI discloses that the local history may be incomplete, while still allowing local ticket creation and showing cached rows.
- Updates carry changed fields and an expected version. A stale update or delete returns a typed version conflict without committing its idempotency receipt. The connected client reads the current ticket, reapplies queued field patches over that version, assigns sequential expected versions, and retries. Mutation-ID conflicts have a distinct error code and are not mistaken for version conflicts. Unchanged fields keep the server's latest values; a queued local patch wins for fields it explicitly changed. A queued delete follows earlier patches.
- Fully local Tauri uses the same ticket contract and validation in the Rust/SQLite adapter. SQLite is authoritative for that profile; no account, API, or network call is required. The local actor ID is `local`. The database remains in the selected local data directory and is not safe for concurrent use from a cloud-synced folder.
- Soft deletion is the normal removal path. Deleting a workspace soft-deletes its tickets in the same transaction and records the actor. Ordinary ticket lists hide deleted rows; sync pages carry tombstones.
- All ticket labels, validation, loading, empty, and error messages are localized in English and Spanish. Controls use the existing shared shadcn-style primitives.

## Consequences

Tickets have the same user-facing fields and workflow in web, connected Tauri, and fully local Tauri. Browser/connected edits remain available offline and are acknowledged as server-synchronized only after the API confirms them. Local desktop remains fully usable without the API and stores durable records in SQLite. Conflicts preserve changes and untouched server fields according to the field-patch rule above; a resource deleted remotely cannot accept a pending update and the mutation stays failed locally. There is no routine physical-delete operation.
